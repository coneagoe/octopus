# 日报 AM/PM 分文件设计

## 问题

当前 `scripts/run.sh` 固定把日报输出到 `output/daily/YYYY-MM-DD.md`，而 `scripts/summarize.py` 会直接覆盖传入的输出文件。

这意味着同一天内如果上午和下午各运行一次，第二次运行会覆盖第一次生成的日报，无法同时保留两个时段的结果。

## 目标

1. 同一天内保留两份日报产物，分别对应上午和下午。
2. 文件名使用用户指定格式：`YYYY-MM-DD-AM.md` / `YYYY-MM-DD-PM.md`。
3. 时段按运行时刻自动判断：12:00 前为 `AM`，12:00 及以后为 `PM`。
4. 不改变现有抓取顺序、缓存读取方式和摘要生成流程。
5. 保持现有 `scripts/run.sh morning` / `scripts/run.sh evening` 调用方式可用。

## 非目标

1. 不把上午和下午写进同一个 Markdown 文件。
2. 不引入新的命令行参数来手动指定 `AM` / `PM`。
3. 不迁移或重写已有的 `output/daily/YYYY-MM-DD.md` 历史文件。
4. 不修改 SQLite 去重逻辑和各抓取器缓存协议。

## 方案对比

### 方案 A：独立文件 + 自动按运行时刻判定（采用）

- `run.sh` 在运行时根据当前小时决定输出 `AM` 或 `PM` 文件。
- `summarize.py` 继续只负责写入调用方指定的输出路径。

优点：

- 改动集中在入口脚本和少量文档/测试，风险低。
- 与用户期望一致，不需要额外人工干预。
- 上午与下午天然写入不同文件，不会互相覆盖。

缺点：

- 手动补跑时，生成哪个文件取决于执行时刻。

### 方案 B：独立文件 + 显式参数决定时段

优点：

- 补跑结果完全可控。
- 测试和重现更直接。

缺点：

- 与“按运行时刻自动判断”的已确认需求不一致。
- 会把“运行标签”和“真实时段”耦合在一起。

### 方案 C：单文件内追加 AM/PM 区块

优点：

- 一天只保留一个日报文件。

缺点：

- 需要处理区块定位、重复追加和重跑覆盖策略。
- 复杂度明显高于当前需求。
- 更容易引入格式漂移和重复内容。

## 最终设计

采用 **方案 A**。

`run.sh` 在生成摘要前计算当前日期和时段后缀，并把输出文件设置为：

- `output/daily/YYYY-MM-DD-AM.md`
- `output/daily/YYYY-MM-DD-PM.md`

`summarize.py` 保持“覆盖指定输出文件”的语义不变，但由于上午和下午输出到不同文件，同一天内两次运行不会再互相覆盖。

## 详细设计

### 1. 输出文件命名

在 `scripts/run.sh` 中：

1. 保留当前 `TODAY=$(date '+%Y-%m-%d')` 的日期来源。
2. 新增时段判断逻辑，基于当前小时生成 `AM` 或 `PM`。
3. 输出路径从 `output/daily/${TODAY}.md` 调整为 `output/daily/${TODAY}-${PERIOD}.md`。

判定规则固定为：

- `00:00` 到 `11:59` → `AM`
- `12:00` 到 `23:59` → `PM`

### 2. 入口兼容性

`scripts/run.sh` 目前接受 `morning` / `evening` 作为位置参数，README 和 cron 示例也沿用这一形式。

本次设计中：

- 该参数继续保留，避免现有调用方式失效。
- 日报文件写入目标不再依赖该参数，而是只依赖实际运行时刻。
- 日志中的“开始运行: $1”保留现状，不把本次需求扩展成统一改名或参数重构。

这样可以把变更范围限制在“日报落盘命名”，避免额外兼容成本。

### 3. 提交信息

当前 `run.sh` 的提交信息为 `Daily update: $TODAY`。

为避免同一天两次提交在语义上过于相似，提交信息同步调整为包含时段，例如：

- `Daily update: 2026-05-13 AM`
- `Daily update: 2026-05-13 PM`

这不会改变 Git 提交流程，只增强可读性。

### 4. summarize.py 的边界

`scripts/summarize.py` 继续保持现有职责：

- 读取 `output/*_cache.json`
- 生成 Markdown 字符串
- 覆盖写入 `--output` 指定路径

不在 `summarize.py` 内部增加“上午/下午”判断，避免把调度语义下沉到摘要生成器里。时段和文件命名仍由 `run.sh` 统一负责。

### 5. 测试

需要补充或调整以下测试：

1. `test/test_run_sh.py`
   - 验证上午运行时会调用 `summarize.py --output .../YYYY-MM-DD-AM.md`
   - 验证下午运行时会调用 `summarize.py --output .../YYYY-MM-DD-PM.md`
   - 验证提交信息包含 `AM` / `PM`

2. 测试稳定性
   - 不直接依赖真实当前时间。
   - 通过可控的时间注入方式，让 shell 测试可以稳定覆盖上午/下午两条路径。

3. `test/test_summarize.py`
   - 原则上无需改动，因为摘要生成器的写文件语义不变。
   - 若新增与输出文件名相关的辅助函数落在 Python 中，再为该函数补单测。

### 6. 文档

README 中所有涉及日报产物和定时运行的说明需要同步更新，明确：

- 日报现在按 `AM` / `PM` 分文件保存
- 现有 cron 示例仍可继续使用
- 同一天上午和下午会生成两份独立日报

## 风险与缓解

- **风险：** 手动在中午后补跑上午任务时，会生成 `PM` 文件。  
  **缓解：** 这是已确认的产品规则；文档中明确“按运行时刻自动判断”。

- **风险：** shell 测试依赖系统时间导致不稳定。  
  **缓解：** 设计要求使用可控时间注入点，而不是直接依赖执行机当前时间。

- **风险：** 历史脚本或外部工具仍读取旧的 `YYYY-MM-DD.md`。  
  **缓解：** README 明确新命名规则；本次只影响后续新生成文件，不改历史文件。

## 实施轮廓

1. 在 `scripts/run.sh` 中引入 AM/PM 计算并更新输出文件名与提交信息。
2. 为 shell 逻辑增加稳定可测的时间控制点。
3. 更新 `test/test_run_sh.py` 覆盖上午/下午产物路径。
4. 更新 README 中的日报产物说明。
