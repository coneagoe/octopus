# 知乎 Cookie 过期错误提示设计

## 问题

当前 `scripts/fetch_zhihu.py` 在知乎登录态失效时，会走“先用 cookie 访问，再尝试账号密码登录”的流程。最终日志里常见的是：

- `知乎登录未完成，可能需要人工处理验证`
- `知乎登录后仍无法访问用户主页`

这些错误能说明抓取失败，但不能稳定表达“现有 `ZHIHU_COOKIES` 已过期或失效”。上游自动化（如 openclaw）读取日志时，难以直接判断这是 cookie 失效，而不是别的 Playwright 或页面异常。

## 目标

1. 当现有知乎 cookie / storage state 失效时，输出稳定、可检索的中文错误提示。
2. 提示中明确指出需要重新导入 `ZHIHU_COOKIES`。
3. 保持现有抓取与容错流程不变：知乎失败仍不阻塞日报主流程。
4. 保持现有缓存语义不变：全部失败时保留旧 `zhihu_cache.json`。

## 非目标

1. 不修改知乎条目提取逻辑。
2. 不改变 `run.sh` 的失败处理策略。
3. 不新增验证码识别、短信登录等自动化能力。
4. 不修改 openclaw 本身的解析逻辑。

## 方案对比

### 方案 A：只改异常文案（采用）

- 在 `fetch_zhihu.py` 中识别“旧 cookie 访问失败”与“自动登录后仍被拦截”这两类认证问题。
- 抛出包含固定关键词的 `FetchZhihuError`。

优点：

- 改动最小。
- 对现有流程影响最小。
- openclaw 直接读取 `fetch_zhihu.py` 输出即可判断原因。

缺点：

- 仅覆盖知乎认证链路，不引入更细粒度的错误分类体系。

### 方案 B：新增认证异常类型

优点：

- 结构更清晰，后续可扩展更多认证错误。

缺点：

- 改动比当前需求更大。
- 对当前目标来说收益有限。

### 方案 C：在 `run.sh` 再包装一层统一错误提示

优点：

- 主日志入口更统一。

缺点：

- openclaw 若直接读取 `fetch_zhihu.py` 输出，仍拿不到最直接的原因。
- 会让错误信息分散在两层脚本里。

## 最终设计

采用 **方案 A**。

在 `fetch_zhihu.py` 中把“cookie 失效”定义为一种明确的认证失败场景，并输出固定中文提示。调用链保持不变，`main()` 仍输出：

`抓取知乎用户失败: <用户名> - <具体错误>`

这样 openclaw 只需读取现有日志，就能看到稳定的失败原因。

## 详细设计

### 1. 识别时机

单个知乎用户抓取时保留当前流程：

1. 先同步 `.env` 中的 `ZHIHU_COOKIES` 到 `output/zhihu_storage_state.json`
2. 用该状态访问知乎用户页
3. 若页面需要登录，则尝试账号密码登录一次
4. 若自动登录后仍需要登录/验证，则判定本次认证失败

其中，第 2 步命中“需要登录”时，说明当前 cookie / storage state 已失效，不再仅仅视为普通登录缺失。

### 2. 错误文案

新增稳定的中文错误文案，要求包含以下信息：

- 现有知乎 cookie 已过期或失效
- 需要重新导入 `ZHIHU_COOKIES`

推荐文案分两类：

1. **旧 cookie 已失效，但后续自动登录也未成功**
   - `知乎 cookie 已过期或失效，且自动登录未完成，可能需要人工处理验证；请重新导入 ZHIHU_COOKIES`

2. **自动登录后仍无法访问用户主页**
   - `知乎 cookie 已过期或失效，自动登录后仍无法访问用户主页；请重新导入 ZHIHU_COOKIES`

以上文案都应作为 `FetchZhihuError` 抛出内容的一部分，避免上游必须依赖内部状态判断。

### 3. 行为边界

以下行为保持不变：

- 若只是当天没有新回答，仍然正常输出 `0 条`
- 若所有知乎用户都失败，仍然保留旧缓存并以非零退出
- `run.sh` 仍然只打印“知乎采集失败，继续执行后续流程”

也就是说，本次改动只增强“失败原因”，不改动“失败后的整体流程”。

### 4. 测试

补充两类测试：

1. 当首次访问命中登录拦截，且自动登录后仍失败时：
   - 断言错误信息包含 `知乎 cookie 已过期或失效`
   - 断言错误信息包含 `重新导入 ZHIHU_COOKIES`

2. `main()` 聚合多个用户失败时：
   - 断言标准输出中保留该明确错误
   - 继续保留旧缓存

## 风险与缓解

- **风险：** 未来知乎还有别的认证失败形态。  
  **缓解：** 文案聚焦“cookie 已过期或失效”这一已确认场景，不阻止后续再细分。

- **风险：** 把所有登录失败都归因为 cookie 失效。  
  **缓解：** 文案中保留“可能需要人工处理验证”，避免误导成纯 cookie 文件损坏。

## 实施轮廓

1. 在 `fetch_zhihu.py` 中抽出/集中认证失败文案。
2. 在 cookie 访问失败且后续登录仍失败的路径中抛出新错误文案。
3. 补单元测试，确保日志对上游稳定可读。
