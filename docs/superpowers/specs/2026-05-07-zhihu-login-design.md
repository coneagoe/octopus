# 知乎登录态抓取设计

## 问题

当前 `scripts/fetch_zhihu.py` 直接以匿名 Playwright 会话访问知乎用户主页。最近定时任务中，目标页面稳定返回 `403`，导致脚本继续解析拦截页并得到 `0` 条结果，最终把 `output/zhihu_cache.json` 写成空数组，使日报看起来像“今天没有知乎内容”。

这个问题有两层：

1. 匿名访问不再稳定，知乎公开主页已对当前抓取方式实施拦截。
2. 抓取失败和“今日确实无新回答”没有被区分，导致缓存和日报语义错误。

## 目标

1. 支持使用 `.env` 中的知乎账号密码建立登录态。
2. 首次登录成功后保存 Playwright 会话，供后续定时任务复用。
3. 当会话失效、页面返回 `403` 或跳转到登录态页面时，自动重新登录一次。
4. 明确区分“抓取失败”和“成功抓到 0 条内容”。
5. 抓取失败时不覆盖现有 `output/zhihu_cache.json`。
6. 保持现有 `scripts/run.sh` 管道结构不变：知乎失败不阻塞其他来源和日报生成。

## 非目标

1. 不改动知乎条目提取的业务范围，仍然只抓“当天回答”。
2. 不引入验证码识别、短信自动接码或其他高风险自动化手段。
3. 不把知乎凭证写入 Git 跟踪文件。
4. 不修改 `summarize.py` 的总体分组逻辑。

## 方案对比

### 方案 A：首次账号密码登录并保存会话，后续复用（采用）

- `.env` 提供 `ZHIHU_USERNAME` 和 `ZHIHU_PASSWORD`。
- 抓取器优先加载本地 `storage_state`。
- 若检测到未登录、`403` 或会话失效，则执行一次登录流程并重新保存会话。

优点：

- 适合 cron 场景，减少重复登录带来的风控压力。
- 自动化程度高，不需要每次手工干预。
- 能把“登录建立”和“内容抓取”收敛在同一脚本中。

缺点：

- 需要维护一次登录流程。
- 会受到知乎登录页结构变动影响。

### 方案 B：每次抓取都用账号密码登录

优点：

- 不依赖本地会话文件。

缺点：

- 更容易触发风控。
- 运行时间更长。
- 定时任务稳定性更差。

### 方案 C：手工登录生成会话文件，抓取器只复用会话

优点：

- 登录流程最稳定，代码最简单。

缺点：

- 自动化不足。
- 会话过期后需要人工重新初始化。

## 最终设计

采用 **方案 A**：在 `fetch_zhihu.py` 中加入“复用会话优先、失效后自动重登”的登录态管理。

## 详细设计

### 1. 环境变量与本地会话文件

`.env` 增加：

- `ZHIHU_USERNAME`
- `ZHIHU_PASSWORD`

新增本地会话文件路径约定：

- `output/zhihu_storage_state.json`

该文件用于保存 Playwright `storage_state`，只保存在本地环境，不提交到 Git。抓取器启动时按以下顺序决定认证方式：

1. 若会话文件存在，先尝试加载该会话访问用户页。
2. 若检测到未登录、`403` 或内容不是目标用户主页，则回退到账号密码登录。
3. 登录成功后立即覆盖写入新的会话文件。

### 2. 抓取前的认证判定

当前 `_fetch_page_content()` 只输出状态码，不对页面是否可用做语义判断。改造后需要把“访问成功但不可抓取”的情况显式识别出来。

推荐判定信号：

1. `page.goto()` 返回 `403`。
2. 页面 URL 停留在登录入口、验证页或其他非用户主页地址。
3. 页面 HTML 中缺少用户主页核心结构，反而出现登录按钮、验证文案或拦截页特征。

只要命中以上任一条件，就不应继续走条目解析，而应抛出明确的抓取失败异常，触发重新登录或上层失败处理。

### 3. Playwright 登录流程

登录流程保持最小化：

1. 打开知乎登录页。
2. 选择密码登录模式。
3. 填写用户名和密码。
4. 提交后等待跳转到已登录页面，或至少等待用户首页/首页导航中的登录态元素出现。
5. 成功后调用 `context.storage_state(path=...)` 写入会话文件。

实现约束：

- 不在日志中输出账号或密码。
- 登录失败时输出中文错误，但不泄露敏感字段。
- 若知乎要求额外验证（例如验证码或二次确认），明确标记为失败并提示人工介入，而不是假装抓取到 `0` 条。

### 4. 用户抓取流程

单个用户抓取建议改成以下状态机：

1. 尝试用缓存会话访问用户主页。
2. 若访问可用，则直接解析当天回答。
3. 若访问不可用，则尝试一次账号密码登录，并在新会话下重新访问用户主页。
4. 若第二次仍不可用，则抛出 `FetchZhihuError`。

这个过程保证每个用户最多触发一次自动重登，避免无限重试。

### 5. 缓存写入语义

`zhihu_cache.json` 的覆盖策略需要调整：

- **至少有一次成功抓取完成**：写入本轮抓取到的聚合结果，即使结果为空，也代表“本轮确实成功检查后没有当天回答”。
- **所有用户都因认证/访问失败而未成功抓取**：保留旧的 `zhihu_cache.json`，不写空数组。

这样日报至少不会把“抓取失败”误表示为“今日无知乎内容”。

### 6. `run.sh` 中的行为

`scripts/run.sh` 保持当前容错思路：

- 知乎步骤失败时记录中文警告。
- 继续执行网站、飞书、邮件和摘要流程。

但日志语义需要依赖 `fetch_zhihu.py` 的新失败类型，让排查者能够从日志中清楚看到是：

- 登录失效
- 页面被 `403`
- 需要人工处理的验证流程

而不是统一落成“0 条新条目”。

### 7. README 更新

README 需要补充：

1. `.env` 中新增的知乎账号配置。
2. 会话文件的用途与位置。
3. 首次启用时需要保证 Chromium 已安装。
4. 当登录态失效或需要额外验证时的恢复方式。

## 错误处理

1. **缺少 `ZHIHU_USERNAME` / `ZHIHU_PASSWORD`**  
   直接报错，说明无法建立登录态。

2. **会话文件损坏或不可解析**  
   忽略旧会话并尝试重新登录。

3. **登录流程未达成登录态**  
   抛出明确异常，终止知乎抓取步骤。

4. **页面访问返回 `403` 或验证页**  
   若尚未重登，则先重登再试一次；若已经重登过，则视为失败。

5. **所有知乎用户抓取失败**  
   不覆盖 `zhihu_cache.json`，并以非零退出码结束知乎步骤。

## 测试计划

1. 为认证判定逻辑补单元测试：
   - `403` 被识别为失败
   - 登录页/验证页被识别为失败
   - 正常用户页被识别为可解析
2. 为缓存策略补单元测试：
   - 全部失败时保留旧缓存
   - 至少一次成功时覆盖缓存
3. 为环境变量读取和会话文件路径补测试。
4. 继续使用仓库现有验证命令：
   - `uv run ruff check scripts/`
   - `uv run pytest test/`
   - `uv run pyright scripts test`

## 风险与缓解

- **风险：** 知乎登录页 DOM 结构变化。  
  **缓解：** 把登录流程封装成小函数，选择尽量稳定的定位策略，并在失败日志中指出是“登录流程失效”。

- **风险：** 登录后仍然遇到风控或二次验证。  
  **缓解：** 明确把这种情况暴露为失败，避免写空缓存；必要时再评估手工初始化会话的备用模式。

- **风险：** 会话文件长期有效性不稳定。  
  **缓解：** 每次检测到失效时允许自动重登一次并刷新会话。

- **风险：** 敏感信息泄露到日志。  
  **缓解：** 禁止记录账号、密码和完整表单值，只记录阶段性状态。
